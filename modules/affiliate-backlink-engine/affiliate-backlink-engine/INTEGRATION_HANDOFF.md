# INTEGRATION_HANDOFF.md

This document describes how the `affiliate-backlink-engine` integrates into the broader ecosystem (PrimeOS, Foundry, AMOS, E.V.E., and product properties such as PantiCandy). It is a contract document: it specifies what the engine exposes, what each external system is expected to provide, and the sequence of calls required to take a campaign from objective to verified acquired link. The engine is built and tested in isolation; this document defines the boundaries across which integration will happen, but no integration is performed by the engine itself. Integration is a follow-on activity that requires its own audit.

The handoff philosophy is contract-first. The engine exposes a typed TypeScript library through `src/index.ts` and a JSON-in/JSON-out CLI through `src/cli/index.ts`. External systems may consume either surface. The library surface is appropriate for in-process composition (for example, a Foundry service that imports the engine as a dependency and calls its functions directly). The CLI surface is appropriate for shell-script orchestration (for example, a PrimeOS pipeline that shells out to the engine and pipes JSON between stages). Both surfaces expose the same contracts: domain types, adapter interfaces, evidence contracts, planner functions, tracker methods, and the verifier function.

## 1. Integration Philosophy

This workspace is isolated. The engine has no runtime dependencies on any canonical repository and performs no network I/O of its own. All external data is reached through adapter contracts (`SearchDataAdapter`, `AiAdapter`) that the caller implements. All verification is reached through the `EvidenceContract` interface and the `verifyAcquiredLink` verifier function callback. This isolation is what allows the engine to be developed, tested, and audited independently of the surrounding ecosystem.

Integration happens via documented contracts only. There are no direct imports from PrimeOS, Foundry, AMOS, E.V.E., or any product repo. The engine's `package.json` declares only development dependencies and a small set of runtime utilities (commander for the CLI); it does not depend on any ecosystem package. The barrel `src/index.ts` re-exports every public type and function, and that barrel is the only legitimate import path for external consumers. Any code that reaches into `src/` subpaths is technically possible but unsupported; future refactors may move or rename internal modules without bumping a major version.

The engine exposes two integration surfaces. The first is the typed library: external systems add `affiliate-backlink-engine` as a dependency and import from the package root, composing modules directly in TypeScript. The second is the CLI: external systems invoke the engine as a subprocess with JSON inputs on stdin or file arguments and parse the JSON output. The two surfaces are functionally equivalent for the operations the CLI exposes; the library surface additionally exposes lower-level building blocks (scoring components, internal-link optimizer, content matcher, risk filter) that the CLI does not surface as standalone commands.

## 2. PrimeOS Integration

PrimeOS is the strategic orchestrator of the ecosystem. In the integrated deployment, PrimeOS sets the campaign objective, selects the target brand and domain, approves risk and campaign strategy, and orchestrates execution across Foundry, AMOS, and E.V.E. The engine's role is to receive PrimeOS's objective as input and return structured opportunities and campaigns for PrimeOS to approve. The engine does not make strategic decisions on PrimeOS's behalf; it computes the tactical substrate (which opportunities exist, how they score, what content work they require, what outreach angle they suggest) and leaves the strategic approval to PrimeOS.

The integration contract is the `planCampaign` and `autoPlanCampaigns` functions in `src/campaigns/planner.ts`. PrimeOS supplies the `siteProfileId`, `brandName`, opportunities (typically produced by the engine's discovery layer, which PrimeOS may invoke via the CLI's `opportunities discover` command or via direct library calls), and optional `contentMatches` and `refreshPriorities`. The engine returns one or more `Campaign` objects whose `objective`, `outreachAngle`, `successCriteria`, `prerequisites`, `contentWork`, and `priority` fields are populated. PrimeOS reviews these fields, applies its own risk and strategy overlays, and either approves the campaign (transitioning it to `OUTREACH_APPROVED` via the tracker) or declines it (transitioning to `DECLINED`).

The engine's tracker records every transition with an `actor` field. When PrimeOS approves a campaign, the transition action should be recorded with `actor: "primeos"` and a note describing the approval. This creates an auditable trail that links each campaign's `OUTREACH_APPROVED` state to a PrimeOS decision. The same applies to declines and to manual overrides. The action log is the integration surface for PrimeOS oversight: PrimeOS can read the `actionsFor(campaignId)` output to reconstruct the full history of any campaign without needing to query the engine's live state.

## 3. Foundry Integration

Foundry is the execution layer of the ecosystem. It runs approved provider, browser, data, and scheduled verification jobs. In the integrated deployment, Foundry is responsible for actually sending outreach emails, fetching pages for re-verification, running periodic revalidation, and performing the live-link check that `verifyAcquiredLink` requires. The engine itself performs none of this I/O; it exposes adapter contracts that Foundry implements and callback functions that Foundry supplies.

The primary adapter contract is `SearchDataAdapter`, declared in `src/adapters/adapter.ts`. A Foundry implementation of `SearchDataAdapter` provides concrete behavior for `search`, `searchBacklinks`, `searchBrokenLinks`, `searchResourcePages`, `searchMentions`, `fetchPage`, and `discoverContacts`. Each method returns `AdapterResult<T>` carrying the data, provenance, confidence, and optional warnings. The engine uses these adapters in its discovery, broken-link, resource-page, and outreach modules. The `FixtureAdapter` shipped with the engine is a reference implementation that reads from local JSON; Foundry's production adapter would replace it with live provider calls.

The second contract is the verifier callback in `verifyAcquiredLink`. Foundry implements the `verifier: () => Promise<{ live, url, detail }>` parameter with a real HTTP or headless-browser fetch. The engine calls the verifier, records the resulting evidence, and transitions the campaign based on the `live` flag. Foundry is also responsible for invoking `tracker.revalidate(campaignId)` on a schedule (the engine recommends a daily or weekly sweep of all active campaigns) so that campaigns past the 30-day inactivity window are flipped to `STALE`. The engine does not run a background timer; it provides the function and expects the caller to schedule it.

## 4. AMOS Integration

AMOS is the content and outreach asset generation layer. It produces supporting content (refreshed pages, new linkable assets, data assets) and outreach assets (drafted emails, personalized context, subject-line concepts). The engine's role is to output content-gap requirements and outreach briefs that AMOS can consume as input, and to receive back the produced content references for inclusion in the campaign's `contentWork.pageIds`.

The engine outputs two structured artifacts for AMOS. The first is the `contentWork` field on a `Campaign`, which declares `description`, `required`, and `pageIds`. When `required` is true, AMOS is expected to produce or refresh the listed pages before the campaign moves from `CONTENT_REQUIRED` to `READY_FOR_OUTREACH`. The second is the `OutreachBrief` interface declared in `src/domain/outreach.ts`, which carries `outreachReason`, `personalizedContext` (with explicit `basis: "observed" | "inferred" | "unknown"`), `targetAsset`, `evidenceIds`, `suggestedSubjectConcepts`, `draftVariants`, `followUpStrategy`, `doNotContact`, `riskFlags`, and a `factInferenceUnknown` breakdown. AMOS consumes this brief to generate final outreach copy; the engine's `draftVariants` are explicitly labeled as drafts, not final copy, and AMOS is responsible for any human review step before outreach is sent.

The engine does not generate final outreach copy. The `AiAdapter` boundary (declared in `src/ai/boundary.ts` and exposed via `NoOpAiAdapter` and `ResilientAiAdapter`) provides classification, drafting, and explanation helpers, but the engine treats their output as suggestions. AMOS is the canonical author of outreach assets in the integrated deployment. When AMOS completes a content refresh, the operator or AMOS updates the campaign's `contentWork` (via `tracker.update`) and transitions the campaign out of `CONTENT_REQUIRED`. The engine records the update and the transition as `CampaignAction` entries for audit.

## 5. E.V.E. Integration

E.V.E. is the verification and provenance auditing layer. It verifies opportunity evidence, acquired-link verification, and the integrity of the evidence log. The engine exposes two contract surfaces for E.V.E.: the `EvidenceContract` interface (declared in `src/domain/evidence.ts` and implemented by `InMemoryEvidenceStore`) and the `verifyAcquiredLink` verifier function (declared in `src/campaigns/tracker.ts`).

The `EvidenceContract` exposes `record(e)`, `for(subjectId)`, `latest(subjectId, kind?)`, and `all()`. E.V.E. uses these methods to audit the evidence backing any campaign, opportunity, or contact. Every actionable claim in the engine is backed by at least one `EvidenceRecord` carrying `kind`, `subjectId`, `claim`, `observedAt`, `source`, `verification`, and an optional sanitized `payload` with a `payloadHash` for tamper detection. E.V.E. can re-compute `canonicalPayloadHash(payload)` (also exported from `src/domain/evidence.ts`) and compare it to the stored `payloadHash` to detect tampering. Evidence records are immutable; updates are made by appending new records, which preserves the full history for audit.

The `verifyAcquiredLink` function is the canonical way for E.V.E. to verify that a claimed acquired link is live. E.V.E. supplies the `verifier` callback (which may be a Foundry-provided fetcher or an independent E.V.E. verifier) and the `recordEvidence` sink (typically an E.V.E.-owned evidence store). The function records an `acquired_link_observation` evidence record with `verification: "VERIFIED"` when the link is live, or an `outcome_observation` with `verification: "UNAVAILABLE"` when it is not. The campaign transitions to `LINK_ACQUIRED` only when the live observation is recorded. E.V.E. may also call `tracker.attachEvidence(campaignId, evidenceId, note?)` to attach additional independent evidence to a campaign without performing a live verification, which is recorded as an `evidence_attached` action.

## 6. PantiCandy / Other Products Integration

Product properties (PantiCandy, vITAL Core, vITAL-Teas, future affiliate sites) supply site inventory, target pages, and competitor datasets to the engine. They receive back campaign outputs and outreach briefs that they use to drive their own content and outreach workflows. The engine is provider-agnostic with respect to which product it serves; the `siteProfileId` field on every entity ties the entity to a specific product property.

The integration surface for products is the site inventory builder (`src/inventory/site-inventory.ts`) and the discovery layer (`src/discovery/discovery.ts`). A product supplies its pages (via JSON import through the CLI's `site import` command, or via direct library calls to `SiteInventoryBuilder`), its competitor set (via the `competitors import` CLI command), and any brand-specific configuration. The engine produces opportunities, scores, content matches, refresh priorities, internal-link recommendations, outreach briefs, and campaigns, all keyed to the product's `siteProfileId`.

The engine ships with three reference workflows that demonstrate the full pipeline for three product archetypes: `examples/panticandy-workflow.ts` (PantiCandy-style affiliate editorial property), `examples/vital-workflow.ts` (vITAL Core-style informational/commerce property), and `examples/generic-workflow.ts` (generic affiliate content site). Each workflow runs the full pipeline using only fixture data and prints a JSON summary. Products can use these workflows as templates for their own integrations, replacing the fixture adapter with a live data source and the in-memory evidence store with a durable store. The product's responsibility is to supply accurate, up-to-date inventory and competitor data; the engine's responsibility is to produce correct, evidence-backed opportunities and campaigns from that data.

## 7. Library API

The library surface is the barrel `src/index.ts`, which re-exports every public type and function in the engine. External systems import from the package root (`affiliate-backlink-engine`) and compose modules directly. The barrel is intentionally flat: it does not impose a particular module structure on consumers, and it does not hide internal modules behind a narrower facade. Consumers who want only a subset of the engine (for example, only the scoring components) pay only for what they import, because the engine is structured as ESM with per-module files.

The exported surface includes the domain types (`Campaign`, `CampaignAction`, `CampaignLifecycleState`, `CampaignType`, `LinkOpportunity`, `EvidenceRecord`, `EvidenceContract`, `OutreachBrief`, `SiteProfile`, `TargetPage`, `RiskFlag`, `ScoreBreakdown`), the lifecycle primitives (`ALLOWED_TRANSITIONS`, `REQUIRES_EVIDENCE_FOR`, `canTransition`, `assertTransition`, `isTerminal`, `CAMPAIGN_LIFECYCLE_STATES`), the planner (`planCampaign`, `autoPlanCampaigns`, `groupOpportunitiesByKind`), the tracker (`InMemoryCampaignTracker`, `verifyAcquiredLink`), the adapter contracts (`SearchDataAdapter`, `AdapterMeta`, `AdapterResult`, `AdapterError`), the reference adapters (`FixtureAdapter`, `CompositeAdapter`, `NoOpAiAdapter`, `ResilientAiAdapter`), the discovery functions, the scoring engine, the risk filter, the content matcher and refresh prioritizer, the internal-link optimizer, the outreach contact discovery and personalization modules, and the site inventory builder.

Library consumers typically compose the engine as follows: build a `SiteInventory`, configure a `SearchDataAdapter` (FixtureAdapter for tests, a live adapter for production), construct an `InMemoryEvidenceStore` (or a durable implementation of `EvidenceContract`), run discovery through `discoverCompetitorBacklinkOpportunities` / `discoverBrokenLinkOpportunities` / `discoverResourcePageOpportunities` / `discoverMentionOpportunities`, score the resulting opportunities through `scoreOpportunity`, plan campaigns through `planCampaign` or `autoPlanCampaigns`, register them with an `InMemoryCampaignTracker`, and verify acquired links through `verifyAcquiredLink`. Each step is independently testable and independently replaceable.

## 8. CLI Handoff

The CLI is the shell-script orchestration surface. It is implemented in `src/cli/index.ts` using the `commander` package and is invoked as `npx tsx src/cli/index.ts <command> [options]` (or as the `backlink-engine` binary after a global install). Every command accepts JSON inputs (either inline via options or via file paths) and produces JSON output when the `--json` flag is passed. The `--out <path>` option writes the output to a file instead of stdout. Human-readable output is the default when `--json` is omitted, which makes the CLI usable interactively as well as in pipelines.

The CLI command groups are `site` (import, analyze), `competitors` (import), `opportunities` (discover, score, list), `broken-links` (analyze), `resource-pages` (analyze), `internal-links` (analyze), `content` (refresh-priorities), `campaign` (create, list, export), and `evidence` (verify). The `campaign create` command wraps `planCampaign` and emits the resulting `Campaign` as JSON, which can be piped into a file or into the next stage of a pipeline. The `campaign list` and `campaign export` commands operate on JSON files of campaigns. The `evidence verify` command exposes the verification path for an external orchestrator that needs to drive `verifyAcquiredLink` via a shell script.

The CLI is suitable for shell-script orchestration because every command is deterministic given the same inputs, every output is JSON-parseable, and every command is idempotent (it does not mutate shared state on disk unless `--out` is specified). A PrimeOS pipeline can chain CLI invocations: `site import` produces an inventory JSON, `opportunities discover --fixture` consumes it and produces an opportunities JSON, `opportunities score` enriches the opportunities with scores, `campaign create` consumes the scored opportunities and produces a campaign JSON, and the campaign JSON is then handed to PrimeOS for approval. The CLI does not maintain a persistent store between invocations; each command reads its inputs from files and writes its outputs to files or stdout, which keeps the pipeline composable and debuggable.

## 9. Example Handoff Sequence

The following sequence walks a single broken-link campaign from objective to verified acquired link, with each ecosystem component performing its designated role. The sequence assumes the integrated deployment; the isolated engine can perform every step except the live outreach and live verification, which require Foundry and E.V.E. respectively.

1. **PrimeOS sets the objective.** PrimeOS calls `planCampaign` (via the library or via `campaign create` on the CLI) with `siteProfileId: "site_panticandy"`, `brandName: "PantiCandy"`, `type: "broken_link"`, and the opportunities previously discovered by the engine. The engine returns a `Campaign` with `state: "DISCOVERED"`, populated `successCriteria`, `prerequisites`, `contentWork`, `outreachAngle`, and `priority`. PrimeOS registers the campaign with the tracker (or receives the tracker-registered campaign back if the engine was invoked with a tracker).
2. **PrimeOS approves the campaign.** PrimeOS reviews the campaign's risk and strategy, then calls `tracker.transition(campaignId, "OUTREACH_APPROVED", { actor: "primeos", note: "Risk + strategy approved." })`. The engine records the transition as a `CampaignAction`. The campaign is now ready for Foundry to execute.
3. **Foundry executes outreach via an adapter.** Foundry implements a `SearchDataAdapter` whose `discoverContacts` method returns verified contact information for the prospects. Foundry sends the first outreach email (using the `OutreachBrief` produced by the engine as input to AMOS, then using AMOS's final copy as the email body). Foundry then calls `tracker.transition(campaignId, "CONTACTED", { actor: "foundry", note: "Outreach email sent." })`.
4. **AMOS generates the draft content from the OutreachBrief.** Before step 3, AMOS consumes the `OutreachBrief` produced by the engine's outreach personalization module. AMOS produces the final outreach copy (subject line, body, follow-up cadence) and returns it to Foundry for sending. AMOS also produces any content refresh or new linkable asset required by the campaign's `contentWork`, and the operator updates the campaign's `contentWork.pageIds` and transitions the campaign out of `CONTENT_REQUIRED` before outreach is sent.
5. **The prospect replies.** Foundry or the operator records the reply by calling `tracker.transition(campaignId, "REPLIED", { actor: "operator", note: "Prospect confirmed interest." })`. If the prospect negotiates terms, the campaign moves to `NEGOTIATING`; otherwise it stays in `REPLIED` pending the live-link check.
6. **E.V.E. verifies the acquired link via `verifyAcquiredLink`.** The prospect places the link. E.V.E. calls `verifyAcquiredLink(tracker, campaignId, verifier, recordEvidence)` where `verifier` is a Foundry-provided HTTP or browser fetcher and `recordEvidence` is E.V.E.'s evidence store. The verifier returns `{ live: true, url: "https://prospect.example/article#pantiCandy" }`. The engine records an `acquired_link_observation` EvidenceRecord with `verification: "VERIFIED"`, records a `link_verified_acquired` CampaignAction with `outcome.kind: "link_acquired"`, and transitions the campaign to `LINK_ACQUIRED`. The campaign is now in its terminal-with-evidence state.
7. **Foundry schedules periodic revalidation.** Foundry invokes `tracker.revalidate(campaignId)` on a schedule (e.g., weekly) for all campaigns not in `LINK_ACQUIRED` or `INVALID`. Campaigns past the 30-day inactivity window are flipped to `STALE` with an audit-trail note. For `LINK_ACQUIRED` campaigns, Foundry schedules an independent re-verification via `verifyAcquiredLink`; if the verifier returns `live: false`, the operator transitions `LINK_ACQUIRED` -> `STALE` -> `DISCOVERED` to restart the lifecycle.

## 10. No Integration Performed in This Mission

Per the project specification, this engine is built and tested in isolation. The contracts documented above are the intended integration surfaces, but no integration with PrimeOS, Foundry, AMOS, E.V.E., or any product property is performed by this codebase. The engine's tests (`tests/`) exercise every public function against fixture data and in-memory stores; no test reaches out to a live provider, sends an email, fetches a live page, or queries an external evidence store. The reference adapters (`FixtureAdapter`, `NoOpAiAdapter`) are deterministic and offline.

Integration is a follow-up activity that requires its own audit. The audit must verify, at minimum, that (a) the `SearchDataAdapter` implementation supplied by Foundry produces evidence with correct `source`, `provenance`, and `verification` fields; (b) the `verifier` callback supplied to `verifyAcquiredLink` performs a real HTTP or browser fetch and returns accurate `live` / `url` / `detail` values; (c) the `EvidenceContract` implementation used in production is durable (the in-memory store shipped with the engine is for testing only and loses its contents on process exit); (d) the `actor` field on every `CampaignAction` is populated correctly by each integrating system so that the audit trail is unambiguous; and (e) the do-not-contact list, risk thresholds, and outreach cadence are enforced by the integrating systems, not by the engine, because the engine's risk module surfaces risk flags but does not enforce outreach suppression on its own.

The engine's non-negotiable rules (no link buying, no fake testimonials, no scraping behind authentication without permission, no bypassing robots/access controls, no spam, no automatic outreach by default, no fabricated metrics, no claiming a backlink exists without evidence, no hardcoded provider) apply equally to the integrated deployment. Any integrating system that violates these rules is in breach of the contract. The engine's design makes such violations detectable: every actionable claim is backed by an `EvidenceRecord`, every transition is recorded as a `CampaignAction`, and the action log is the integration surface for oversight. An auditor who reads the action log and the evidence store can reconstruct what was claimed, what was verified, who approved it, and when it happened.
